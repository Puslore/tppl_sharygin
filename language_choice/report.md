## 1. Обработка больших данных в реальном времени

### Парадигма

**Параллельная потоковая / конвейерная обработка данных** с системной императивной реализацией.

### Язык программирования

**C++**, при необходимости с использованием **CUDA C++**, OpenCL, SIMD-интринсиков и специализированных библиотек захвата изображений.

### Обоснование

Исходные требования очень жёсткие:

- разрешение: `4096 × 4096`;
- глубина цвета: 16 бит на пиксель;
- частота: 100 кадров в секунду.

Объём сырых данных:

4096 × 4096 = 16 777 216 пикселей на кадр
16 бит = 2 байта на пиксель
16 777 216 × 2 = 33 554 432 байта на кадр
33 554 432 × 100 ≈ 3.36 ГБ/с

То есть система должна принимать и обрабатывать примерно **3.36 гигабайта сырых данных в секунду**, или около **1.68 гигапикселей в секунду**. На каждый кадр остаётся около **10 мс**.

Для такой задачи важны:

- минимальные накладные расходы на память и управление потоками;
- предсказуемая производительность;
- возможность использовать многопоточность;
- поддержка SIMD-инструкций;
- возможность выносить обработку на GPU или специализированные ускорители;
- работа с большими буферами без лишнего копирования;
- контроль над временем жизни объектов и аллокациями.

**Почему выбран C++:**

1. C++ позволяет писать высокопроизводительный системный код с низким уровнем абстракции.
2. Есть зрелая экосистема для обработки изображений: OpenCV, Intel IPP, Eigen, CUDA, OpenCL, Vulkan compute и другие инструменты.
3. Можно строить конвейер обработки: захват кадра → передача в буфер → предобработка → анализ → принятие решения.
4. Можно эффективно использовать многоядерные CPU, GPU и FPGA-ускорители.
5. Подходит для долгоживущих систем, работающих в режиме 24/7, при аккуратной архитектуре, тестировании и контроле ресурсов.

Важная оговорка: **только выбор языка не гарантирует выполнение требований**. Поток данных очень большой. На одном обычном сервере без специализированного ввода/вывода, DMA, высокоскоростных интерфейсов захвата, нескольких вычислительных узлов или GPU/FPGA такая обработка в реальном времени может быть невозможна. Поэтому здесь нужен не только язык, но и правильная аппаратная архитектура.

Тем не менее, с точки зрения языка программирования и парадигмы наиболее рациональный выбор — **C++ и параллельная конвейерная обработка данных**.

## 2. Прототип ML-сервиса для прогноза погодных условий

### Парадигма

**Императивная скриптовая разработка** с элементами **пайплайнов обработки данных**.

### Язык программирования

**Python**.

### Обоснование

Ключевые требования:

- запустить MVP за 2 недели;
- использовать готовые ML-библиотеки;
- быстро итерировать;
- часто менять алгоритмы;
- прогноз выполняется 1 раз в сутки.

Здесь критична не максимальная скорость выполнения программы, а скорость разработки, экспериментов и проверки гипотез.

**Почему выбран Python:**

1. Python является фактическим стандартом для прототипирования машинного обучения.
2. Есть огромное количество готовых библиотек:
    - `scikit-learn`;
    - `XGBoost`;
    - `LightGBM`;
    - `CatBoost`;
    - `PyTorch`;
    - `TensorFlow`;
    - `pandas`;
    - `NumPy`;
    - `statsmodels`;
    - `MLflow` и другие инструменты для экспериментов.
3. Удобно быстро проверять гипотезы в интерактивной среде:
    - Jupyter Notebook;
    - VS Code;
    - Google Colab;
    - Databricks.
4. Данные с метеорологических датчиков удобно загружать, очищать и преобразовывать с помощью `pandas`.
5. Прогноз выполняется 1 раз в сутки, поэтому требования к задержкам и производительности в реальном времени низкие.
6. Для прототипа важнее скорость разработки, чем максимальная эффективность исполнения.

**Почему выбрана такая парадигма:**

Для задачи прогнозирования погоды удобно строить процесс как последовательность шагов:
загрузка данных с датчиков
→ очистка и нормализация
→ генерация признаков
→ обучение модели
→ валидация
→ прогноз
→ сохранение результата

Это хорошо ложится на **пайплайн данных** и императивный стиль разработки. На этапе прототипа такой подход позволяет быстро менять алгоритмы, сравнивать модели и получать результат за короткий срок.

Для долгосрочной продакшен-версии позже можно добавить более строгую архитектуру, тесты, контейнеризацию и планировщик задач. Но для двухнедельного MVP Python — наиболее оправданный выбор.

## 3. Интерактивный UI для торгового терминала

### Парадигма

**Реактивная / событийно-ориентированная парадигма** с **однонаправленным потоком данных**.

### Язык программирования

**TypeScript**.

### Обоснование

Требования:

- веб-интерфейс;
- 50+ виджетов;
- данные в реальном времени;
- реакция быстрее 16 мс;
- сложные взаимодействия между виджетами;
- потоки данных из WebSocket, REST API и локальных событий;
- код должен быть легко тестируемым.

Для такого интерфейса главной сложностью является не просто отрисовка, а управление состоянием и потоками событий.

**Почему выбран TypeScript:**

1. Это стандартный язык для сложной веб-разработки.
2. Статическая типизация уменьшает количество ошибок при большом количестве компонентов и виджетов.
3. Хорошо поддерживается редакторами кода, что ускоряет разработку.
4. Позволяет строить надёжную архитектуру вокруг событий и состояний.
5. Совместим с популярными веб-фреймворками и библиотеками:
    - React;
    - SolidJS;
    - Svelte;
    - Angular;
    - RxJS;
    - Redux Toolkit;
    - MobX;
    - Zustand и др.
6. Подходит для написания легко тестируемого кода.

**Почему выбрана реактивная парадигма:**

Торговый терминал получает данные из разных источников:
WebSocket
REST API
действия пользователя
локальные события интерфейса
обновления котировок
изменения портфеля
изменения настроек виджетов

Если менять состояние напрямую и хаотично, система быстро станет сложной и нестабильной. Реактивная модель позволяет представить изменения как потоки событий.

Пример архитектурной идеи:
событие из WebSocket
→ нормализация
→ обновление глобального состояния
→ пересчёт зависимых данных
→ обновление только изменённых виджетов

Однонаправленный поток данных улучшает тестируемость:

- события можно моделировать в тестах;
- состояние можно проверять как чистые данные;
- логику обновления можно вынести в чистые функции;
- UI можно тестировать отдельно от источников данных.

Для выполнения требования `< 16 мс` одного языка недостаточно. Дополнительно понадобятся:

- виртуализация списков;
- мемоизация;
- декомпозиция компонентов;
- избежание лишних перерисовок;
- использование `Web Workers` для тяжёлых вычислений;
- обновление только изменённых частей интерфейса;
- возможно, `Canvas` или `WebGL` для очень насыщенных графиков.

Но именно **TypeScript + реактивная событийная архитектура** дают хорошую основу для сложного, быстрого и тестируемого торгового веб-интерфейса.

## 4. Прошивка для устройства регистрации температуры

### Парадигма

**Императивная / процедурная встраиваемая разработка** с обработкой прерываний и детерминированным планированием.

### Язык программирования

**C**.

### Обоснование

Требования:

- микроконтроллер с 256 КБ Flash и 32 КБ RAM;
- работа от батареи;
- минимальное энергопотребление;
- прямой доступ к GPIO, ADC, UART;
- детерминированное время отклика;
- переносимость между разными микроконтроллерами.

Для таких ограничений лучше всего подходит максимально простой и предсказуемый системный язык без тяжёлой среды выполнения.

**Почему выбран C:**

1. C является основным языком встраиваемых систем.
2. Компиляторы C доступны практически для всех микроконтроллеров.
3. Можно писать код без динамической аллокации, сборщика мусора и тяжёлых библиотек.
4. Обеспечивается предсказуемое потребление памяти.
5. Можно напрямую работать с регистрами периферии.
6. Легко контролировать энергопотребление и переводить устройство в спящие режимы.
7. Код можно делать детерминированным, если избегать недетерминированных операций и использовать простой планировщик или прерывания.
8. Для большинства микроконтроллеров существуют зрелые SDK, HAL-библиотеки, примеры и документации именно на C.

**Почему выбрана процедурная/императивная парадигма:**

Прошивка датчика температуры обычно строится из понятных модулей:
инициализация тактирования
инициализация GPIO
инициализация ADC
инициализация UART
чтение датчика
фильтрация значения
запись в журнал
передача данных
переход в режим низкого энергопотребления

Это естественно ложится на процедурный стиль.

Для переносимости между разными микроконтроллерами следует разделить код на слои:
Прикладной слой
    логика измерения температуры, журналирование, энергосбережение

Слой абстрагирования платы
    общие интерфейсы для ADC, UART, GPIO, таймеров

Слой конкретного микроконтроллера
    прямой доступ к регистрам и настройкам конкретного MCU

То есть прямой доступ к регистрам нужен, но его лучше вынести в тонкий платформенно-зависимый слой. Тогда основная логика остаётся переносимой.

Альтернативой мог бы быть **Rust**, так как он тоже подходит для встраиваемых систем и даёт безопасность памяти. Однако для данной задачи **C** практичнее из-за более широкой поддержки микроконтроллеров, зрелости инструментов, простоты, предсказуемости и большого количества готовых примеров от производителей железа.
